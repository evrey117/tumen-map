# Управление жилыми комплексами

## Что уже работает

Кнопка «Управление ЖК» открывает панель создания, редактирования, удаления с подтверждением, геокодирования и выбора/перемещения метки, отмены черновика, резервного экспорта, истории и подготовки восстановления. Ни токенов, ни паролей вводить не нужно.

Единственный действующий список: `public/data/residential.json` в main. Исходные 17 ЖК мигрированы без удаления, включая приблизительные точки и предупреждения. Старый homes.json оставлен как архив координат, но больше не управляет картой. Социальные и промышленные данные не изменены.

Карта получает общие данные из публичного GitHub raw, обновляет их каждые 60 секунд при видимой вкладке, при возврате во вкладку и по кнопке ↻. При недоступном GitHub использует встроенный снимок. Кэш CDN может задержать видимость свежего коммита; успешный workflow также обновляет снимок сайта. Данные редактирования не хранятся в localStorage; черновик существует только в памяти вкладки до закрытия/перезагрузки.

## Почему нужен ещё один шаг владельца

GitHub Pages исполняет только публичный JavaScript и не может безопасно хранить ключ записи в репозиторий. Поэтому панель готовит запрос, а постоянную запись выполняет GitHub Actions **после входа владельца в GitHub и ручного подтверждения Run workflow**. Посетители могут подготовить личный черновик, но не изменить общие данные.

Исходник workflow сохранён в `deployment/manage-homes.yml`. Владелец уже одобрил активацию слиянием PR №1: рабочая копия находится в `.github/workflows/manage-homes.yml`, а workflowEnabled=true в `public/admin-config.json`. Право **GitHub Actions contents: write** в save-job уже разрешено владельцем; визуальная доработка его не меняет. Это право технически относится к содержимому репозитория, а не только к одному файлу; серверный скрипт ограничивает изменения фиксированным residential.json. Его нельзя описывать как файловое ограничение самого токена.

Для повторной установки в другом репозитории активация требует отдельного подтверждения: перенести подготовленный workflow в `.github/workflows/manage-homes.yml` и установить workflowEnabled=true в public/admin-config.json. Для удобства можно подготовить отдельный PR только с этими двумя изменениями. Его слияние владельцем и будет явным разрешением. Никакие платные сервисы, OAuth-приложения, персональные токены или новые секреты не требуются. Видимость репозитория, branch protection и общие настройки безопасности не меняются.

## Как сохранять после активации

1. На карте нажмите «Управление ЖК».
2. Добавьте/выберите ЖК, заполните данные, найдите адрес. Выберите подходящий результат, при необходимости передвиньте метку. Подтвердите координаты.
3. Нажмите «Применить в черновик». Можно подготовить несколько изменений. Удаление подтверждается отдельно.
4. Нажмите «Подготовить сохранение в GitHub», затем «Скопировать запрос» и «Открыть GitHub».
5. Войдите аккаунтом **evrey117**. На странице workflow нажмите **Run workflow**, выберите **main**, вставьте запрос в **change_request**, нажмите зелёную **Run workflow**.
6. Дождитесь зелёного результата. Вернитесь в панель и нажмите «Проверить сохранение». Изменения получат остальные устройства и посетители.

Редактирование формы без применения не входит в запрос: панель предлагает сначала применить или отменить его. Запрос не является секретом или ключом доступа: сам по себе он не даёт права записи. При необходимости можно вручную скачать резервную копию черновика. Неподтверждённые результаты геокодера и ручные точки остаются приблизительными, а не выдаются за независимую адресную проверку.

## История и восстановление

«История и восстановление» загружает последние 30 коммитов residential.json из GitHub. Выберите версию, подтвердите восстановление в черновик, затем сохраните тем же способом. Восстановление создаёт новый коммит; старая история остаётся. Сервер читает выбранный файл из реального коммита-предка main, не доверяет присланному клиентом содержимому якобы старой версии.

## Защита

- Только workflow_dispatch на main и только actor ID владельца репозитория. Ни issues, ни pull_request, ни произвольные HTTP-запросы не запускают запись.
- Проверка владельца повторяется серверным скриптом. Проверка по скрытой кнопке не используется; статус workflowEnabled — только подсказка интерфейса.
- Весь пакет изменений проверяется до записи: схема, уникальные ID, обязательные поля, конечные координаты в пределах Тюмени, источник OSM. Пути файлов пользователь не задаёт.
- SHA-256 исходного файла проверяется и в панели, и перед записью. Устаревший запрос отклоняется; сервер не перезаписывает более свежие изменения молча.
- Сохранения сериализованы concurrency group. Push обычный, без force. Сбой проверки не меняет репозиторий.
- GITHUB_TOKEN существует только во временном runner GitHub Actions. Токен не передаётся браузеру и не попадает в JSON, localStorage или исходный код.
- Save-job получает contents:write только после активации владельцем; publish-job использует уже существующие Pages/OIDC-разрешения. Публикуется точный SHA коммита данных.

Администраторы самого GitHub-репозитория и установленные владельцем интеграции по-прежнему подчиняются существующим правам GitHub; этот интерфейс не может отменить их полномочия. На момент проверки единственный человеческий collaborator репозитория — evrey117.

## Проверки и ограничения текущего этапа

Unit-тесты проверяют создание, изменение, удаление, отклонение постороннего пользователя и устаревшей версии, реальное сохранение во временный Git-репозиторий и восстановление из его истории. Браузерные тесты проверяют панель, отмену удаления/черновика, геокодер (явный тестовый ответ), подтверждение координат, историю, конфликт и два клиента общего источника.

Активация владельцем подтверждена слиянием PR №1. Живое административное сохранение в рамках визуальной доработки не выполнялось, чтобы не менять общие данные. Для его отдельной проверки владельцу нужно выполнить контрольное сохранение и восстановление, проверить общий JSON с двух устройств и успешное обновление Pages. Наличие активного workflow само по себе не является подтверждением успешного контрольного сохранения.
